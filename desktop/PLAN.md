# ADB Shell Desktop — план переноса на Electron

Стек: **Electron** (выбран за надёжность/обкатанность — VS Code, Slack,
Discord, Figma Desktop; не самый современный из рассмотренных, но самый
проверенный в продакшене). Цель — не просто "порт под Windows", а со
временем единая кроссплатформенная замена macOS-версии на Swift (Electron
одинаково собирается под Windows, macOS и Linux из одной кодовой базы).

Живёт в этом же репозитории, в `desktop/` — не трогает `Sources/`,
`Package.swift`, Swift-тесты и CI. Полностью независимый Node/TypeScript
проект.

## Статус

- [x] Фаза 0 — каркас проекта, тулинг
- [x] Фаза 1 — реальный Electron-процесс (main/preload/renderer), список
      устройств в окне, подключение по IP
- [x] Фаза 2 — вкладка "Приложения": список (system/user), детали,
      runtime-разрешения (выдать/забрать), force-stop/очистка
      данных/enable-disable/удаление. Отдельная вкладка "Библиотека APK"
      (см. ревизию v0.4.0 ниже) переносит локальный каталог .apk и
      проверку обновлений через F-Droid. **Не перенесено**: экспорт/импорт
      наборов приложений, снапшот устройства, тегирование файлов
      библиотеки, drag-and-drop в окно, полный "Инфо"-лист с разрешениями
      из манифеста — самостоятельные, менее приоритетные куски
- [x] Фаза 3 (частично) — Shell-раннер (без истории/избранного/broadcast) и
      файловый браузер (навигация, mkdir, удаление). **Не перенесено**:
      push/pull через нативные диалоги выбора файла, макросы (движок
      переменных + JSON импорт/экспорт) — не начаты
- [x] Фаза 4 — Wi-Fi ADB, проброс портов (forward/reverse), свойства
      устройства с поиском — всё в одной вкладке "Инструменты"
- [x] Фаза 5 (частично) — вкладка "Мониторинг": CPU/RAM/батарея (опрос раз
      в 2с, как в Swift-версии), спарклайн CPU за последние 30 отсчётов,
      список процессов с kill. Вкладка "Logcat": живой стрим (долгоживущий
      `adb logcat` процесс в main, строки уходят в renderer через IPC-
      событие, а не invoke), фильтр по тексту/тегу/уровню, подсветка по
      уровню, очистка буфера устройства. **Не перенесено**: зеркалирование
      экрана через scrcpy, снапшоты устройства, экспорт истории
      мониторинга в CSV, просмотр ANR/tombstone — зеркалирование
      требует вшивать/спавнить scrcpy и управлять его окном, снапшоты —
      писать zip-архивы (в Node нет built-in зип-райтера) — оба
      достаточно самостоятельные куски работы, отложены
- [x] Фаза 6 — упаковка (electron-builder: NSIS для Windows, zip для
      macOS), иконки, `adb.exe` + DLL вшиты в Windows-сборку через
      vendor/win/ + win.extraResources. Проверка обновлений — см. ревизию
      v1.0.0 ниже (уведомление + ссылка на релиз, не electron-updater:
      полноценное автообновление ненадёжно без Developer ID + нотаризации)
- [x] Фаза 7 — desktop-release.yml публикует настоящий GitHub Release по
      тегу `desktop-v*.*.*` (отдельный неймспейс от `v*.*.*` Swift-версии).
      Проверено вживую: тег `desktop-v0.2.0` → реальный релиз с
      `ADB Shell Setup 0.2.0.exe` (83 МБ, NSIS) и `ADB Shell-0.2.0-arm64-
      mac.zip` (99 МБ) — https://github.com/andrei-s96s/adb-shell/releases/tag/desktop-v0.2.0

Проверено вручную через Chrome DevTools Protocol (не только `node --test`
для чистой логики, но и реальный запуск Electron + проверка живого DOM) —
поймано и исправлено минимум два реальных бага именно так: двойное
исполнение classic-скрипта рендерера и отсутствующие `.js`-расширения в
относительных импортах (TypeScript `moduleResolution: "bundler"` не
добавляет их сама, а нативный ESM в браузере требует явно).

### Ревизия v0.3.0 — баги, найденные целевым прогоном

- **Вся навигация была заблокирована без выбранного устройства** —
  `#content` целиком прятался, пока не выбрано устройство. Тот же класс
  ошибки, что уже чинили в Swift-версии для библиотеки APK. Теперь вкладки
  видны всегда, каждый экран сам показывает подсказку «нет устройства».
- **CSP тихо блокировал inline `style=""` атрибуты** в разметке (проверено
  вживую — `getComputedStyle` возвращал не заданную ширину, а "auto") — JS
  `element.style.x = y` при этом продолжает работать. Перенесено в CSS-классы.
- **`clearDeviceBuffer()` не обрабатывал `'error'`** на дочернем процессе —
  необработанное `'error'` на EventEmitter валит весь main-процесс Electron.
- **Гонка в `LogcatSession.stop()`** — старый процесс мог успеть прислать
  ещё несколько строк ПОСЛЕ stop(), они утекали в renderer под тем же
  serial, если сразу следом стартовал новый стрим. Слушатели теперь
  снимаются до kill().
- **`install()`, `disconnect()`, `pair()` были в AdbService/IPC, но без
  единого способа вызвать их из интерфейса** — добавлены кнопка
  «Установить APK…» (с нативным диалогом выбора файла), кнопка отключения
  у сетевых устройств в списке и форма сопряжения по коду в сайдбаре.
- **HTML-инъекция через `innerHTML` с данными устройства** (getprop,
  dumpsys, `ps`) в нескольких экранах — CSP снижает реальный ущерб (блокирует
  инлайн-скрипты), но полагаться только на это не стоит. Переведено на
  `textContent`/`createElement` везде, где раньше был string-interpolated
  `innerHTML`.

### Ревизия v0.3.1 — «не открывается на Mac», «криво на Windows»

- **macOS: Gatekeeper жёстко отклонял скачанный .app** ("ADB Shell.app
  is damaged and can't be opened") — CI-сборка (без Developer ID, GitHub
  Actions macos-latest: "0 valid identities found") наследовала ad-hoc
  подпись от прекомпилированного Electron.app, которая переставала быть
  валидной после того как electron-builder докладывал app.asar и прочие
  ресурсы в Contents/Resources, но повторной полной подписи не происходило.
  Подтверждено вживую: `spctl -a -vvv --type execute` на скачанном (с
  `com.apple.quarantine`, симулирующим реальное скачивание браузером)
  артефакте возвращал `code has no resources but signature indicates
  they must be present` — это жёсткий блок, не мягкое предупреждение
  "неизвестный разработчик". Исправлено хуком `afterSign`
  (`scripts/afterSign.js`), который запускает `codesign --force --deep
  --sign -` на полностью упакованном `.app` — тот же приём, что уже
  использует `build_app.sh` для Swift-версии. После фикса: `Sealed
  Resources` заполнены, ошибка исчезла, повторно собранный и
  квалифицированный (той же симуляцией) .app реально запускается.
- **Windows/везде: чекбоксы в `.toolbar` раздувались и наезжали на
  соседний текст** — `.toolbar input { flex: 1; padding: 8px; border:
  1px solid ...; background: ... }` был рассчитан на текстовые поля, но
  как обычный descendant-селектор ловил и `<input type="checkbox">`
  внутри `.checkbox-label` (чекбоксы "системные" на вкладке Приложения и
  "автопрокрутка" на Logcat) — вместо маленького нативного чекбокса
  получалась раздутая плашка с рамкой и фоном на flex:1, конкурирующая за
  место с соседними полями и текстом подписи. Баг платформонезависимый по
  природе (чистый CSS-селектор), но по описанию ("поля наползают на
  текст") и понятной разнице в рендеринге чекбоксов между Chromium на
  Windows и на Mac — главный подозреваемый на роль "криво на Windows".
  Исправлено: `.toolbar input:not([type='checkbox'])` для текстовых
  полей, отдельный сброс `.toolbar input[type='checkbox']` до нативного
  вида. Проверено вживую через CDP (computed style + getBoundingClientRect)
  на обоих местах использования — чекбокс 13×13px без padding/border/фона,
  соседние элементы toolbar не пересекаются.

### Ревизия v0.3.2 — наложение на вкладке «Приложения» осталось

- Пользователь сообщил, что текст "Выберите приложение слева" всё ещё
  наползает на кнопку "Установить APK…" даже после v0.3.1. Причина шире,

  ниже intrinsic-content ширины (`min-width: auto` — поведение flex-item
  по умолчанию). Проверено вживую через CDP на СТАНДАРТНОМ окне 1200×760
  (не только на гипотетическом узком Windows-окне): содержимое toolbar
  занимало ~364px при доступных 320px — элементы уже вылезали за границу
  `.panel-left` (у которой нет `overflow: hidden`) и визуально

  `flex-wrap: wrap`, текстовым полям задан `min-width: 80px` (даёт
  явный пол сжатия и переопределяет `auto`). Проверено вживую через CDP

### Ревизия v0.4.0 — Библиотека APK (список без устройства + F-Droid)

Пользователь спросил, как открыть готовый список APK без подключённого
устройства и проверить их на обновления — в Electron-версии этой функции
не было вообще (осознанно отложена на Фазе 2). Перенесена спецификация
Swift-версии (`ApkLibraryViewModel`, `ApkBadgingParser`, `FDroidUpdateChecker`)
почти механически, с тем же набором тестовых кейсов:

- Новая вкладка "Библиотека APK" — доступна и без устройства (тот же
  принцип, что и у остальных вкладок после фикса device-gating): список
  локальных .apk из настраиваемого каталога (по умолчанию
  `Documents/AdbShell/APK`, путь сохраняется между запусками — простой
  JSON вместо UserDefaults), добавление файлов, скачивание по прямой
  ссылке, показ в Finder/проводнике, удаление.
- Установка на устройство — единственное, что требует serial (кнопка
  неактивна и подсказывает причину без устройства); отдельная кнопка
  "На все устройства" ставит на все готовые последовательно и сообщает
  успехи/ошибки по каждому.
- Проверка обновлений с F-Droid: читает манифест каждого .apk через вшитый
  `aapt2 dump badging` (тот же бинарник и версия, что `build_app.sh`
  вшивает для Swift-версии под macOS — добавлен Windows-классификатор
  через новый `scripts/fetch-aapt2.js`, вшивается в обе сборки через
  `build.mac`/`build.win` extraResources) и сверяет versionCode с
  публичным `https://f-droid.org/api/v1/packages/<pkg>`. Ничего не
  скачивает без явного нажатия — только показывает бейдж с доступной
  версией; кнопка "Обновить" скачивает конкретный файл и заменяет старый.
  Если aapt2 не вшит (например, кастомная сборка), проверка тихо
  недоступна — список и обычная установка продолжают работать.
- Проверено: `parseApkBadging`/`parseFDroidResponse` — теми же кейсами,
  что и Swift-тесты (`ApkBadgingParserTests`, `FDroidUpdateCheckerTests`);
  вживую — реальный aapt2 на реальном .apk (старая сборка самого
  F-Droid-клиента) корректно прочитан, реальный запрос к f-droid.org нашёл
  настоящее новое обновление, полный путь через UI (вкладка → список →
  бейдж → кнопки) проверен через CDP, кнопка "Установить" корректно
  недоступна без устройства.
- Сознательно не перенесено (см. Фазу 2 выше): тегирование, drag-and-drop,
  полный "Инфо"-лист манифеста — самостоятельные куски, отложены.

### Релиз v1.0.0 — целевой аудит + проверка обновлений

Полный прогон на баги/вёрстку перед первым "стабильным" релизом, плюс
давно отложенная проверка обновлений. Всё найдено и проверено тем же
CDP-прогоном (реальный Electron + живой DOM), что и раньше — не только
чтением кода:

- **Окно без минимального размера** — `.panel-left` (320px, не сжимается)
  и другие фиксированные колонки не переживают произвольное сжатие окна
  пользователем. Прогон через CDP на принудительно суженном viewport
  (~650px) воспроизвёл реальное наложение на вкладках "Приложения" и
  "Инструменты". Добавлены `minWidth: 920` / `minHeight: 600` для
  `BrowserWindow` (при 900px и шире переполнений не возникает ни на одной
  вкладке) — проверено вживую через AppleScript: попытка сжать окно до
  400×400 реально ограничивается до 920×600.
- **`grid-template-columns: 1fr 1fr` вместо `minmax(0, 1fr) minmax(0, 1fr)`**
  в `.tools-grid` и `.monitor-stats` — та же ловушка intrinsic-content
  минимума, что и у flex (см. v0.3.2), только для CSS grid: трек не
  сжимается меньше содержимого и раздувает всю сетку. Исправлено в обоих
  местах.
- **Иконка приложения — белые углы на Windows** (сообщено пользователем
  напрямую). Причина найдена и подтверждена побайтово: исходный
  `Resources/AppIcon.icns` (используется и Swift-версией, и десктоп-портом)
  содержит НЕПРОЗРАЧНЫЕ БЕЛЫЕ пиксели в углах вокруг скруглённого
  квадрата иконки вместо прозрачности — на macOS это незаметно, потому что
  Finder/Dock сами маскируют любую иконку под скруглённый квадрат, а
  Windows Explorer/таскбар рендерит иконку как есть, без такой маски,
  показывая сплошной белый угол. Подтверждено побитово (`(255,255,255,255)`
  в углу вместо ожидаемого `(0,0,0,0)`) и визуально (см. приложенные
  скриншоты сравнения в истории сессии). Пересобраны `build/icon.ico` и
  `build/icon.icns` напрямую из векторного `Resources/AppIcon.svg` через
  `rsvg-convert` + `png-to-ico`/`iconutil`, минуя лишний раунд-трип через
  сам `.icns` — прозрачность в углах подтверждена побайтово после
  пересборки. `Resources/AppIcon.icns` (используется Swift-сборкой)
  сознательно не тронут — это территория параллельной сессии, баг там
  просто не проявляется визуально из-за маскировки Finder/Dock.
- **main-процесс без глобального перехвата ошибок** — необработанное
  исключение или promise rejection вне `ipcMain.handle` (который сам
  сериализует брошенное в отклонённый промис для renderer) по умолчанию
  просто валит весь процесс без единого сообщения — то самое "приложение
  просто не открылось". Добавлены `process.on('uncaughtException'/
  'unhandledRejection', ...)` с `dialog.showErrorBox`.
- **`ApkLibraryService`'s `fs.mkdirSync` в конструкторе не был обёрнут в
  try/catch** — конструктор выполняется на верхнем уровне `main.ts` до
  `app.whenReady()`; если каталог `Documents/AdbShell/APK` недоступен
  (права, OneDrive-редирект на Windows и т.п.), необработанное синхронное
  исключение там роняет весь процесс ДО открытия хоть одного окна.
- **Три пропущенных обработчика ошибок в renderer**, найденные
  прицельным чтением всех `void asyncFn()`-вызовов: `chooseDirectory()` и
  `apkLibrary:revealInFileManager`-обработчик в `apkLibrary.ts` (второй —
  `shell.openPath` вообще не бросает исключение, а резолвится строкой с
  текстом ошибки, обычный try/catch её не поймает без явной проверки), и
  вызов `refreshPortForwarding()` в `tools.ts` при смене устройства — все
  три либо ничего не показывали пользователю при ошибке, либо оставляли
  необработанный promise rejection.
- **Проверка обновлений** (давно отложенный пункт из "Технических
  решений" — "electron-updater пока не начато"). В отличие от
  Swift-версии (`UpdateService.swift`, полноценная подмена `.app` на
  лету), здесь — только уведомление со ссылкой на страницу релиза,
  осознанно без автозамены файла: macOS-сборка подписана лишь ad-hoc
  (не Developer ID + нотаризация, на которые рассчитан Squirrel.Mac под
  electron-updater), так что надёжное автообновление сейчас технически
  недостижимо и рискует само стать новым "не открывается". Использует
  список `/releases` (не `/releases/latest`!) с явным фильтром по
  префиксу тега `desktop-v` — репозиторий публикует ОБЕ линейки тегов
  (`v*.*.*` у Swift-версии и `desktop-v*.*.*` у этой) в одном списке
  релизов, и `/releases/latest` отдал бы самый свежий по дате релиз
  вообще, какого бы трека он ни был. Проверка раз за запуск (не polling),
  ничего не показывает при ошибке сети — не должна мешать обычной работе.
  **Побочная находка**: у самой Swift-версии `UpdateService.isNewer` в
  паре с `/releases/latest` в теории может принять свежий `desktop-v*`
  релиз за релиз собственного трека (тримминг только `v`/`V` с концов
  строки не убирает префикс `desktop-` целиком) — код Swift-версии не
  трогался (территория параллельной сессии), но стоит проверить там же.
- Проверено: `npm run typecheck`, `npm test` (64/64, +5 новых для
  compareVersions/findLatestDesktopRelease), CDP-прогон на 1200×760 и на
  принудительно суженных viewport (900/650px) по всем вкладкам без единой
  находки переполнения на ≥900px, тёмная тема (`prefers-color-scheme`)
  проверена вживую и работает корректно, консоль без ошибок/warning при
  проходе по всем вкладкам.

## Почему именно так по фазам

Портируется не код, а **спецификация**: каждый существующий Swift-парсер
(`ADBService.parseDevices`, `GetpropParser`, `PortForwardParser`,
`IpRouteParser`, `ApkBadgingParser`, `DumpsysParser` и т.д.) уже имеет
входные/выходные данные, зафиксированные в Swift-тестах (`Tests/AdbShellTests/`)
— их переносим на TypeScript почти механически, с тем же набором тестовых
кейсов. Это самая низкорисковая часть работы и сделана в первую очередь.

UI-слой переносится экраном за экраном, используя работающее Swift-
приложение и его локализацию (`Localization/ru.lproj`, `en.lproj`) как
эталон поведения и копирайта — не гадаем формулировки заново.

## Технические решения

- **Язык**: TypeScript, компилируется через `tsc` в `dist/` — Electron
  использует собственный встроенный Node/V8, полагаться на нативную
  поддержку TS в системном Node (26+) внутри Electron не стал —
  стандартный и предсказуемый путь.
- **Тесты**: встроенный `node --test` (без Jest/Vitest) — для чистых
  функций парсинга этого достаточно, лишняя зависимость не нужна.
- **UI**: пока простой HTML/CSS/TS без фреймворка — экран небольшой
  (список устройств + shell), фреймворк (React и т.п.) добавим при
  реальном разрастании интерфейса на Фазе 2+, а не заранее.
- **Тема**: цвета/шрифты из `Sources/AdbShell/Design/Theme.swift` (CP.*)
  переносятся как CSS custom properties — визуальная преемственность.
- **Бинарники**: `adb.exe`/`scrcpy`/`aapt2` под Windows — те же источники,
  что `build_app.sh` использует под macOS, просто Windows-сборки; скрипт
  загрузки будет добавлен на Фазе 6 вместе с упаковкой.

## Что уже НЕ будет портироваться как есть

- Самообновление через подмену `.app`/бинарника на лету (electron-updater
  и его Squirrel.Mac/NSIS-механизмы) — рассчитано на настоящую подпись
  Developer ID + нотаризацию на macOS, без них ненадёжно и само рискует
  стать новым "не открывается". Вместо этого — проверка версии по GitHub
  Releases и уведомление со ссылкой (см. ревизию v1.0.0), пользователь сам
  скачивает и ставит новую версию вручную, как при первой установке.
- Сканирование QR с камеры — уже убрано и из Swift-версии (не работало
  надёжно, неудобно на ноутбуке) — в порт не добавляем вообще.
